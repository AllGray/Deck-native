# M2: the A64 decoder

Status, 2026-11-03: done. The decoder is generated from a pattern table and agrees with LLVM 23's disassembler on **every one of the
12,505,492 words** in the text of Pokopia 2.0.1 (`main`, `sdk`, `subsdk0`, `rtld`): 0 differences, no documented exceptions
needed, and the same 7 undecodable words. It also agrees on about 60 million synthetic words (section 4).

## 1. Design

```
src/a64/a64.tbl ──┐                       build/…/gen/nxw/a64_gen.hpp   enum class Op, Fields<Op>
src/a64/names.tbl ┴─ gen_a64.py (build) ─▶ build/…/gen/a64_gen.cpp       decode(), name/field/pattern tables, print_body()
                                               + src/a64/print.cpp        Printer: one method per operand kind
```

- **`a64.tbl`**: one line per instruction encoding (765), with a name, a 32-bit pattern with named fields, optional exclusions and
  decode condition, an architecture-extension tag, and an LLVM-style operand format, followed by the line's aliases.
- **`names.tbl`**: operand names that LLVM prints, generated by `tools/gen_names.py` (section 2.2).
- **`gen_a64.py`**: runs at build time (CMake custom command, Python 3.10+ in isolated mode). It checks the table (32 bits per
  pattern, unique names, exclusions against field widths) and writes:
  - the `Op` enum and a `Fields<Op::X>` struct per encoding, with a constexpr constructor that extracts the named fields;
  - `decode(uint32_t) -> Op`: a decision tree of `switch` statements on runs of up to 7 bits fixed in every remaining candidate,
    splitting on single bits where no bit is common, and ending in short masked-match lists that keep table order;
  - `print_body()`: one `case` per op that extracts the fields, tries the aliases in order, and emits the format.
- **API** (`include/nxw/a64.hpp`): `decode(w)`, `Fields<Op>(w)`, `op_fields(op)`/`field(w, info)` for generic access,
  `op_name`, `op_encoding` (mask, value, extension), and `print(w, pc)`. Unallocated words return `Op::Unallocated` and print
  as `<unknown>`.
- **Printer** (`print_impl.hpp`, `print.cpp`): about 50 small methods (registers, immediates, shifts and extends, SIMD
  arrangements, lists and lanes, system operands). It exists for the cross-check and for debugging (`a64-dis`).

Ops follow the Arm ARM's instruction pages: base instructions keep `sf`/`size` and ordering bits as fields (`CAS` covers
cas/casa/casal/casl/casb/cash…; `LDADD` covers ldadd{a}{l}{b|h} and its `stadd` alias), while each FP and AdvSIMD instruction
has its own op (`FADD`, `FADD_v`, `FMLA_ve`, `LD4_lane_post`, …), so the lifter can switch on the op directly.

## 2. Table format

```
NAME  <pattern, MSB first>  [!field=bits[,field=bits]…]  [@ext]  [? <C++ condition>]  | <format>
= <C++ condition> | <format>                       alias, tried in order (first true one is printed)
```

- Pattern tokens: `0`/`1` runs are fixed bits, `x` runs are ignored, `name` is a 1-bit field and `name:N` an N-bit field.
- `!` excludes words whose fields match (`x` = any). `?` is a decode condition over the fields, used where the reserved set is
  not a few bit patterns (bitmask immediates, AdvSIMD lane forms).
- Formats are LLVM assembly with `{helper arg, …}` calls; arguments and conditions are C++ expressions over the fields, `w` and
  `pc`. ` | ` with spaces separates the parts, so a bitwise or is written `a|b`.

Examples:

```
ADD_imm      sf 0 0 100010 sh imm12:12 Rn:5 Rd:5 | add {rsp sf, Rd}, {rsp sf, Rn}, {aimm imm12, sh}
= sh == 0 && imm12 == 0 && (Rd == 31 || Rn == 31) | mov {rsp sf, Rd}, {rsp sf, Rn}
ORR_imm      sf 01 100100 N immr:6 imms:6 Rn:5 Rd:5 ? logimm_ok(sf, N, immr, imms) | orr {rsp sf, Rd}, {r sf, Rn}, {uimm bitmask(N, immr, imms, 32 << sf)}
= Rn == 31 && !any_movw(bitmask(N, immr, imms, 32 << sf), 32 << sf) | mov {rsp sf, Rd}, {imm sext(bitmask(N, immr, imms, 32 << sf), 32 << sf)}
CAS          size:2 001000 1 L 1 Rs:5 o0 11111 Rn:5 Rt:5 @lse | cas{s ar(L, o0)}{s bh(size)} {r size == 3, Rs}, {r size == 3, Rt}, [{xsp Rn}]
FMLA_ve      0 Q 0 01111 1 sz L M Rm:4 0001 H 0 Rn:5 Rd:5 !sz=1,L=1 !sz=1,Q=0 | fmla {va Rd, 2 + sz, Q}, {va Rn, 2 + sz, Q}, {ve M << 4|Rm, 2 + sz, sz ? H : H << 1|L}
```

### 2.1 Decode boundaries

The encodings come from the Arm ARM's A64 encoding index (Dynarmic's `a64.inc` was not needed). Where the manual leaves a
choice, LLVM's decoder decides:
- should-be-one/zero bits that LLVM treats as "unpredictable" are ignored (`x`): Rs/Rt2 of the exclusive and ordered loads and
  stores, Ra of SMULH/UMULH, Rs of LDAPR, CRm of SB, CFINV, XAFLAG and AXFLAG. CAS and CASP keep Rt2 = 11111 fixed, as LLVM does.
- reserved values are rejected exactly where LLVM rejects them (1D arrangements, half precision without FP16, bad bitmask
  immediates, odd CASP and 128-bit register pairs, and so on).
- a few encodings outside v8.0–8.5 are decoded because LLVM decodes them whatever the feature set; they are tagged so the lifter
  can trap on them: SMSTART/SMSTOP (`@sme`), `msr PM` (`@ebep`), RPRFM (`@rprfm`), MRRS/MSRR/SYSP (`@sysreg128`), and
  MSR/MRS with op0 = 0 (`@llvm`; architecturally unallocated, LLVM prints them as `S0_*` registers). The v8.6–8.9 hint names
  (dgh, stshh, …) live in the hint name table.

### 2.2 Name tables

`names.tbl` holds the names LLVM prints for system registers (MRS and MSR separately), SYS aliases (ic, dc, at, tlbi, cfp,
cpp, dvp, apas), hints, DMB/DSB/ISB options, PSTATE fields, and PRFM/RPRFM operations. `tools/gen_names.py` enumerates each of
these small spaces in full through llvm-objdump and keeps only the named entries; the printer builds the generic forms
(`S3_0_C13_C0_2`, `sys #…`, `hint #…`) itself. The script also checks that MRRS/MSRR use the same names as MRS/MSR.

## 4. The cross-check

`a64-xcheck` (in `src/a64/tools/`) does the following:
- wraps the words in a minimal AArch64 ELF relocatable (as `research/census/xcheck_llvm.py` does), written to a scratch folder;
- runs one `llvm-objdump -d -z --mattr=+v8.5a,+crypto` (LLVM 23.1.4) and streams its output;
- checks that every line's raw word matches the input word (so the two streams cannot drift);
- normalises LLVM's line by dropping the symbol annotation (` <.text+0x44>`), `//` comments (`// =0x4000`) and tabs;
- compares it with our `print(w, pc)`.

`+v8.5a` brings LSE, RCpc and PAC with it: adding `+lse,+rcpc,+pauth` gives byte-identical output on main and sdk. Without `--mattr`, llvm-objdump
enables every AArch64 feature (SVE, SME, MTE…), which is what the census compared against.

Every word either matches exactly, matches through a documented rule (`tools/xcheck_rules.hpp`), or counts as unexplained. The
rule list is **empty**: the printer reproduces LLVM's spelling directly. This includes:
- its hex and decimal choices (`#0x10` but `lsl #3`, `bfi …, #16, #4`, `svc #0`, `dcps1`, `brk #0`, decimal post-increments of
  vector loads);
- the MOVZ > MOVN > ORR preference for `mov`;
- the bitfield alias order;
- the `lsl` spelling of extends next to SP;
- `movi d0, #0000000000000000` (printf `%#016llx`);
- `hint #39` versus `hint #0x2f`.

## 5. Performance

On the i9-13900KF, single-threaded, Release build:
- **decoding** takes 6.8–8 ns a word on game code: 70 ms for main's 10.3 M words, about 85 ms for all 12.5 M. Random words take
  14 ns, because the tree's branches are less predictable.
- **decoding plus printing** takes about 100 ns a word, 1.3 s for all modules.
- **a full cross-check of the four modules** takes 21 s, almost all of it spent in llvm-objdump.

## 6. Tests

- `a64-tests` (ctest) runs 65 hand-made encodings with the expected op, fields and LLVM text. They cover bitmask immediates
  (including reserved ones and the `mov` preference), shifted, extended and register-offset operands, bitfield aliases, SIMD
  element, indexed, lane and modified-immediate forms, load/store pair modes, system registers and SYS aliases, PAC (hints,
  RETAB, PACIA, LDRAA), LSE sizes and orderings (CAS, CASP, LDADD with stadd, SWP, LDAPRB), and branch targets. They also check
  the typed `Fields<Op>` accessors.
- `a64-xcheck-patterns` (ctest) runs `a64-xcheck --patterns 200` against LLVM. It needs no game data.

## 7. Re-running

```
scripts\build.cmd                                                  (builds nxw_a64, a64-xcheck, a64-dis, a64-tests)
py -3 -I src\a64\tools\nso_text.py <ExeFS dir> _local\a64          (decompressed text segments; game code stays in _local)
build\Release\bin\a64-xcheck.exe _local\a64\main.text              (likewise sdk, subsdk0, rtld; add --ops FILE for op counts)
build\Release\bin\a64-xcheck.exe --patterns 3000 --scratch _local\a64
build\Release\bin\a64-xcheck.exe --space ffc00000 d5000000 --scratch _local\a64
build\Release\bin\a64-dis.exe d503237f c8edfd4e                    (op, fields and text for single words)
ctest --test-dir build\Release -R a64
py -3 -I src\a64\tools\gen_names.py _local\a64 src\a64\names.tbl   (only when moving to a new LLVM)
```

The ExeFS used here is `installer-test-win\build201\extract\ExeFS`. `a64-xcheck` exits with 1 when any difference is
unexplained. It runs one llvm-objdump at a time and deletes its temporary ELF.

## 8. Notes for M3

- Lift on `Op` plus `Fields<Op>`. Printing and aliases are only for humans and the cross-check.
- The `@llvm` ops (MSR_S0, MRS_S0) and the LLVM-parity extras should become traps or "unexpected instruction" in the lifter.
  None of them occurs in the game.
- `HINT` carries the PAC hint forms (pacibsp, autibsp, xpaclri, …) and BTI. The lifter decides on `CRm:op2`.
- Open issue: none for the decoder. The ExeFS of 1.0.5 has not been checked yet. Running the same commands on its dump would
  settle that.
